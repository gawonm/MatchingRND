# LLM 모델 통일 및 호출 방식 개선

## 기존 방식과 해결하려던 문제

브랜치별 LLM 설정이 달라 실행 조건을 비교하기 어려웠다. RFP 관련성 판정은 후보를 묶는 기존 최적화가 있었지만, 같은 문서의 보유기술 A와 요청기술 B를 별도로 호출했다. 이에 따라 같은 원문을 다시 보내고, 문자 수 제한으로 배치가 나뉘는 비용이 남아 있었다. ORC 질문의 기존 전체 실행은 97회, 956,740토큰, 약 11분 45초였다.

목표는 **정답 후보의 회수를 확인하면서 전체 질문 처리의 LLM 호출·토큰·비용·시간을 줄이는 것**이다. RFP 구간 지표와 최종 답변까지의 전체 지표는 구분했다.

LLM 기본값은 입력 해석·나눔기술·NTIS·RFP·Gap·최종답변·평가에서 `gpt-5.6-luna`로 통일했다. 아래 실험은 기존 방식까지 같은 모델로 실행했으므로, 개선율은 모델 교체나 파인튜닝의 효과가 아니다. 요청 구성과 배치 방식을 비교한 결과다.

## 검토한 방법

| 방식 | 변경 내용 | 기대 효과와 위험 |
| --- | --- | --- |
| 기존 | A/B 별도 판정, 후보 최대 5개·24,000자 기준 배치 | 동일 원문의 반복 전송·호출이 남음 |
| ① 통합·문자 배치 | 한 문서에 A/B 목록을 함께 제공하고 기술별로 판정 | 중복 요청 감소, 독립 판정·인용 검증 필요 |
| ② 통합·토큰 배치 | ①에 메시지·스키마의 예상 토큰 수 기준 배치 적용 | 입력 예산 활용 개선, 묶음에 따라 판정이 달라질 가능성 |
| ③ 관련 원문 우선 | 관련 원문·이웃 조각을 먼저 제공하고 불확실하면 전체 재판정 | 입력 축소 기대, 핵심 근거 누락 위험 |
| ④ 순서 개선·검토 예산 | A/B 어휘 대응으로 순서를 바꾸고 일정 검토 후 결과가 있으면 중단 | 호출 감소 기대, 뒤쪽 정답 누락 위험 |
| ③+④ | 원문 선택과 검토 순서·예산 결합 | 두 효과와 위험을 함께 확인 |

②는 원문을 자르거나 후보를 버리는 방식이 아니다. 최대 5개까지 묶고, 메시지·응답 스키마의 `o200k_base` 예상 토큰 수에 2,048 여유분을 더해 기본 32,000토큰 예산을 적용한다. 큰 단일 문서는 그대로 단독 호출한다. 실제 사용량·비용은 API usage로 측정했다.

각 과제의 job 인덱스·기술 인덱스·원문 인용을 검증한다. 배치 형식에 누락·중복·범위 오류가 있으면 개별 호출로 재판단한다. A/B와 서로 다른 과제의 근거를 섞지 않도록 지시하고 검증한다.

## 검증 설계

사용자가 제공한 정답40 CSV를 참고했다. 시간·토큰 절약 요청에 따라 10문항으로 줄였다. 원래 ORC 질문 Q1과 abstention 사례 Q7을 포함하고 완료 결과를 재사용하도록 선택했다. 문항은 Q1·Q3·Q7·Q9·Q10·Q13·Q14·Q19·Q21·Q28이다. 정답 회수 결과로 선택하지 않았지만 무작위 대표 표본도 아니다.

- 질문 해석·검색 후보·RFP 원문을 문항별 한 번 고정해 여섯 방식에 제공했다. 정답은 평가에만 사용했다.
- 10문항 × 6개 방식, 조합별 1회다. 완료된 21개 결과를 재사용하고 39개 조합을 추가 실행했다.
- 명시적 PARTIAL·DIRECT 정답 RFP가 있는 문항은 6개이며 정답 문서도 6개다. 동일 원본 파일의 중복·하위 과제는 원본 코드별 별칭으로 묶어 회수를 판정했다.
- 정답표에 없는 후보를 전부 오답으로 간주하지 않았다. 전체 정확도·precision은 산출하지 않았다.
- 앱 캐시는 문항·방식별로 분리했다. 서버 캐시 읽기·쓰기는 실제 usage에 따라 비용에 반영했다.
- 시간은 동시 작업 6개 조건의 RFP 필터 구간이며 질문 해석·검색·NTIS·Gap·최종 답변 생성은 제외한다.

| ① | 235 | 2,732,926 | $0.7529 | 132.2초 | 3/6 |

| ④ | 169 | 1,937,835 | $0.4165 | 90.8초 | 2/6 |
| ③+④ | 202 | 2,320,426 | $0.5700 | 96.7초 | 2/6 |

②는 기존 대비 호출 78.1%, 토큰 60.8%, 추정 비용 63.1%, 평균 필터 시간 49.6% 감소를 관측했다. ① 대비로는 호출 46.0%, 토큰 약 5.2%, 비용 약 11.0%, 평균 시간 약 24.8% 감소했다. 시간·비용에는 서버 캐시와 응답 변동도 영향을 주므로 모든 감소를 배치 변경만의 인과 효과로 단정하지 않는다.

③·③+④에서는 실제 원문 축소가 한 번도 발동하지 않았다. 다만 excerpt 모드의 추가 지시문은 적용됐다. 따라서 ③의 수치를 원문 축소 효과로 설명할 수 없다. ④·③+④는 이 실행에서 정답 회수가 2/6이었다. Q21 정답은 실제 검토 후 탈락했으므로 이 누락을 조기 종료 탓으로 단정할 수도 없다.

## ①·② 추가 검증과 남은 품질 문제

과거 ORC 히트펌프 오탐과 기존 판정 차이를 기준으로 Q1·Q7·Q13·Q14의 경계 사례를 선정했다. 같은 5개 후보 묶음·원문·순서를 유지하고 seed 0·1로 각각 실행했다. seed 0은 기존 설정 재실행이고 seed 1은 설정 변화에 대한 민감도 진단이다. 추가 API 호출은 총 44회였다.

| 방식 | 호출 | 토큰 | 추정 USD | seed 간 판정 일치 | 기존 seed 0과 재실행 일치 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ① | 28 | 315,321 | $0.0367 | 19/20 | 17/20 |
| ② | 16 | 301,062 | $0.0251 | 19/20 | 17/20 |

같은 seed에서 ①·②는 34/40 일치했다. 일치율은 정확도가 아니며 경계 사례 표본을 전체 품질로 일반화할 수 없다. 44개 요청은 모두 `gpt-5.6-luna`, HTTP 200이었고 배치 형식 오류 fallback은 없었다.

- ORC 질문의 히트펌프는 이번 반복에서 두 방식 모두 두 번 제외했다. 과거 전체 실행의 ②는 적합한 ORC RFP를 1순위, 히트펌프를 2순위로 반환했다. 1순위 실패와 추가 후보 오탐을 구분해야 한다.
- Q14의 공조기 진단→원전 이상감시 질문에서 ②는 ORC 후보를 두 번 통과시켰다. 적용 대상 차이를 인정하면서도 넓은 상태 감시·진단 기능으로 similar를 부여했다. 과도한 일반화가 의심되는 재현 사례이며 품질 개선이 필요하다.
- Q7의 후보 반환 여부는 진단 지표다. CSV가 전체 코퍼스에 후보가 없다고 확정하지 않았으므로, 반환 자체를 곧바로 오답으로 단정하지 않는다.
- Q3·Q9·Q19 정답은 검색 후보에 있었지만 A/B 근거 부족으로 탈락했다. PARTIAL 정답 기준과 현행 필터 조건의 차이를 점검해야 한다.

## 전체 응답과 NTIS 추가 개선

원래 ORC 질문을 입력 해석부터 최종 답변까지 실행한 기존 실측이다.

| 방식 | 전체 호출 | 전체 토큰 | 추정 비용 USD | 전체 응답 시간 |
| --- | ---: | ---: | ---: | ---: |
| 기존 | 97 | 956,740 | $0.2954 | 704.9초 |
| ① | 68 | 611,409 | $0.1997 | 577.4초 |
| ② | 47 | 547,317 | $0.1730 | 535.6초 |

② 실행은 기존 대비 호출 51.5%, 토큰 42.8%, 추정 비용 41.4%, 전체 시간 24.0% 감소했다. 단, NTIS 응답에 따라 RFP 검색 질의·후보가 달랐던 한 문항·한 번의 관측이다. 전체 감소율을 RFP 코드 변경만의 효과로 발표하면 안 된다.

② 전체 실행은 입력 해석 1 + 나눔기술 1 + NTIS 19 + RFP 17 + Gap·최종 답변 9 = 47회였다. NTIS 19회 중 과제별 기술 추출이 10회여서, 전체 호출을 더 줄이기 위한 다음 대상으로 검토했다.

NTIS 원문을 최대 5개씩 묶어 추출하는 옵션을 구현했다. 과제 인덱스로 원래 순서를 복원하고, 근거를 해당 과제 원문과 대조하며 실패한 과제만 개별 재처리한다. 같은 과제 10개에서 호출 10→3회, 토큰 12,254→9,839, 추정 비용 $0.009116→$0.006378를 관측했다. 3회는 배치 두 번과 개별 재처리 한 번을 포함한다.

그러나 추출 기술요소가 93→57개로 달랐고 중요한 내용의 누락 여부는 확인되지 않았다. 요소 수 자체가 정확도는 아니지만 품질 유지의 근거도 부족하다. **NTIS 추출 배치는 실험 옵션으로 남기고 기본값은 개별 추출로 유지한다.** 변경 이후 전체 파이프라인을 재실행하지 않았으므로 47회에서 7회를 차감한 값을 새 전체 실측으로 제시하지 않는다.

## 선택 근거와 최종 적용

**RFP는 ② A/B 통합·토큰 배치를 기본값으로 선택했다.** 전체 호출 절감 목적에서 직접적인 효율 이점이 있고 10문항의 명시 정답 회수는 기존·①과 같았다. 추가 반복에서도 ①의 안정성이 더 높다고 입증되지 않았다. ④는 더 저렴했지만 이 실행에서 정답 회수가 줄었고, ③은 축소 효과 자체를 검증하지 못했다.

“②의 품질이 동등함을 입증했다”는 결정은 아니다. 효율 우위와 관측된 정답 회수를 근거로 선택하되 오탐·누락은 개선 과제로 남긴다.

| 설정 | 최종 상태 |
| --- | --- |
| 공통 LLM | `gpt-5.6-luna`, 명시적 환경변수·CLI override는 지원 |
| RFP 판정 | A/B 통합, 기술별 독립 판정·인용 검증 |
| RFP 배치 | 기본 `tokens`, 32,000 추정 토큰, 최대 5개 |
| 원문·순서 | 전체 원문·검색 순서, 추가 검토 예산 제한 없음 |
| 문자 배치 복귀 | `RFP_RELEVANCE_BATCH_MODE=chars` |
| ③·④ | 명시적으로 활성화하는 실험 옵션, 기본 비활성 |
| NTIS 추출 | 기본 `NTIS_EXTRACTION_BATCH_SIZE=1`, 5는 실험용 |

모델은 `app/common/llm_config.py`, RFP 판정·토큰 계산은 `app/rfp_rag/retrieval/eligibility.py`, 배치 구성·검증은 `app/common/relevance_batch.py`에서 관리한다. NTIS 추출 실험은 `app/ntis_rag/generation/batched_extraction.py`에 분리했다.

## 공유 자료와 발표 문구

최종 기본 설정 변경 후 백엔드 테스트 256개가 통과했다. 토큰 기본 배치가 문자 예산으로 분리되는 입력을 더 적은 요청으로 처리하는지, 결과·근거 검증이 유지되는지 확인하는 회귀 테스트도 포함한다. 프런트엔드 소스는 이번 변경에서 수정하지 않았다. 앞선 통합 검증에서는 프런트엔드 테스트 69개·빌드·lint가 통과했으나, 이번 셸에서는 `npm`을 찾을 수 없어 프런트엔드 검증을 재실행하지 못했다.

불필요한 실험 콘솔 로그 14개와 실행하지 않은 로컬 임시 스크립트 2개를 제거했다. `.gitignore`의 남은 병합 주석을 정리하고 실험 콘솔 로그 재추적을 방지했다. 학습 스크립트가 실제로 읽는 초안 데이터, 원본 자료, 모델 설정, 구조화 평가 결과와 테스트는 보존했다. API 키·로컬 캐시·원본 대용량 출력은 커밋하지 않는다.

[평가 기록 JSON](evaluations/llm_call_optimization_20261018.json)에 비교 요약·문항별 수치·추가 호출 usage·원본 CSV SHA-256·실험 조건을 보존했다. API 키와 환경설정 원문은 포함하지 않는다. 상세 기록은 [추가 검증](RFP_PRESENTATION_VALIDATION_20261018.md), [10문항 비교](RFP_DATASET_OPTIMIZATION_20261017.md), [ORC 전체 비교](RFP_OPTIMIZATION_BENCHMARK_20261017.md)에 있다. 과거 문서의 기본값·권장 설명은 당시 상태이고 현재 적용 상태는 본 문서와 코드 기준이다.

비용은 [OpenAI 공식 요금표](https://developers.openai.com/api/docs/pricing) 기준 API usage 추정액이다. 캐시 읽기·쓰기를 구분했고 reasoning 토큰을 출력에 중복 가산하지 않았다. 실제 청구액을 확인한 것은 아니다.

> 같은 LLM 모델에서 반복되던 RFP A/B 판정을 통합하고, 문자 수 대신 예상 토큰 수로 요청을 묶었다. 고정한 10문항의 RFP 구간에서 호출 78.1%, 토큰 60.8%, 추정 비용 63.1% 감소를 관측했고 명시 정답 회수는 기존과 같은 3/6이었다. ORC 질문의 별도 전체 실행에서도 97→47회를 관측했다. 품질 동등성은 입증하지 않았으며 과도한 관련성 판정과 PARTIAL 정답 누락은 개선 과제로 남아 있다.
