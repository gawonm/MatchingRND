# RFP 전처리와 검수

현재 로컬 `data/raw/rfp`의 PDF를 읽습니다. 원본은 수정하지 않습니다.
GitHub main을 기준으로 RFP 추출·파싱·청킹만 변경했으며, 이전 임시 진단 스크립트와 검색 출력 변경은 제거했습니다.

## 처리 방식

1. PDF 좌표가 겹친 동일 문자를 제거합니다. 서로 다른 위치에 있는 반복 글자는 유지합니다.
2. 표에서 추출된 텍스트와 실제 단어 좌표를 대조하고, 빠진 단어·빈 제목 셀을 복원합니다.
3. 품목번호와 명시된 제목을 기준으로 과제를 구분합니다. 총괄·세부 관계와 이어지는 페이지를 보존합니다.
4. 공고 앞부분과 다른 별첨은 과제 본문에 섞지 않습니다. 제목이 불명확하거나 OCR 페이지를 지나 경계가 불명확해진 구간은 검수 대상으로 보관합니다.
5. 개발내용·목표·성능표·지원조건·보충 원문을 항목별로 청킹합니다. 청크에는 과제명·품목번호·총괄명이 포함됩니다.
6. 원문 블록의 과제 연결, 원문 인용 일치, 청크로의 전달, 페이지 기록, 총괄 참조를 자동 검사합니다.

## 로컬 실행

프로젝트 루트의 패키지가 설치된 환경에서:

```powershell
python -X utf8 -m app.rfp_rag.preprocessing --output-dir data/processed/rfp/review
```

추출기 캐시는 `db/rfp/cache`에 저장됩니다. 변경된 추출기는 구버전 캐시를 그대로 사용하지 않습니다.
토크나이저는 기존 로컬 모델 캐시에서 읽습니다. 이 명령은 LLM 호출·임베딩 생성·Supabase 쓰기를 하지 않습니다.

## 결과 확인

| 파일 | 내용 |
|---|---|
| `review.md` | 전체 PDF의 처리 상태와 상세 결과 링크 |
| `manifest.json` | 파일별 과제·청크 수, 누락·검수 항목, 처리 버전 |
| `files/*.json` | 과제·청크·출처 좌표와 원문 블록 연결 기록 |
| `tasks.json` | 연결된 총괄·세부 과제와 항목 원문 |
| `chunks.json` | 임베딩에 사용할 청크와 출처 |

상태의 의미:

- `automatic_checks_passed`: 기계적 출처·연결 점검을 통과했습니다. 모든 의미적 연결이 맞다는 보장은 아닙니다.
- `review_required`: 제목 복원, 병합 성능표, OCR 또는 불확실한 경계 등을 확인해야 합니다. 정상 추출된 부분은 보존합니다.
- `failed`: 파일을 처리하지 못했습니다. 이유와 원본 파일을 확인해야 합니다.

과제에 연결되지 않은 원문도 `issues`의 `audit` 기록에 남습니다. `context`는 공고·목차 등 문맥,
`quarantine`은 소속을 확정하지 못한 구간입니다. OCR이 필요한 페이지는 경고로 남으며 자동으로 내용을 추측하지 않습니다.
필요한 원문이 context/quarantine에 남은 경우 검수한 뒤 규칙 또는 해당 문서 연결을 보완해야 합니다.

## 재적재 전 확인

- `missing_chunk_blocks`, `invalid_source_quotes`, `unaccounted_pages`, `orphan_children`를 확인합니다.
- `review_required`에서 과제 제목·품목번호·개발내용이 올바르게 연결됐는지 원본과 대조합니다.
- 과제 0개인 파일은 순수 공고문인지, 실제 RFP를 놓쳤는지 구분합니다.
- 검수 보류 원문이 남아 있으면 전체를 정상 데이터로 간주해 일괄 재적재하지 않습니다.

## 검수 판정의 검색·적재 반영

`app/rfp_rag/review_decisions.json`에 원본 SHA-256과 과제별 판정을 기록합니다.
`review.py`는 로컬 인덱스와 Supabase 적재에 동일하게 적용됩니다.

- 자동 검사 통과 과제는 유지합니다. 미검수 경고가 있는 새로운 파일은 기본 보류합니다.
- 복원 제목은 원문과 대조한 값을 사용하고, 불확실한 과제와 그 하위 과제는 검색에서 제외합니다.
- 확인된 RFP 페이지 범위만 연결하며 신청서 양식·공고 공통 설명은 재연결하지 않습니다.
- 병합 성능표의 미확인 부분은 청크, 중복 텍스트, 구조화 `metrics`에서 제외합니다. 다른 개발내용은 유지합니다.
- OCR 대상에 기술정보가 있으면 연결된 과제는 추가 추출·검수까지 보류합니다. 표지·로고·목차는 별도 기술 근거로 사용하지 않습니다.
- 원본 해시나 판정에 참조한 과제 ID가 달라지면 재검수를 요구합니다. 판정을 무시하고 적재하지 않습니다.

```powershell
python -X utf8 -m app.rfp_rag.preprocessing --output-dir data/processed/rfp/validated
python -X utf8 -m app.rfp_rag.review
python -X utf8 -m app.scripts.supabase_rag ingest --modules rfp
```

`data/processed/rfp/approved/review.md`에서 사용할 과제와 보류 과제를 확인합니다.
`validated`에는 수정 전 추출·감사 기록이, `approved`에는 검수 필터를 적용한 결과가 남습니다.
검수 결과 JSON의 `hold`는 원본 삭제를 뜻하지 않습니다. 사용자 지시로 삭제한 6개 PDF의 목록은
`validated/deleted_files.json`에 따로 보존했습니다.

적재 시 RFP 코퍼스만 트랜잭션으로 교체합니다. 기술나눔·NTIS·법령·기업 코퍼스는 갱신하지 않습니다.
원본 PDF와 생성된 검수 JSON·임베딩 캐시는 로컬 자료이며 GitHub 커밋에는 포함하지 않습니다.

DB에는 검색에 필요한 원문·좌표·블록 ID·검수 상태를 저장합니다. 각 문장에 반복되던 전체 표의
`cells/rows/headers` 사본은 전송하지 않으며, 동일 과제 목록도 한 번만 저장합니다.
원본 표와 전체 추출 메타데이터는 로컬 `validated/files` 감사 기록에 남습니다.
